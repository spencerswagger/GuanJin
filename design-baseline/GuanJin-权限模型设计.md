# 关津 · 权限模型设计

| 项目 | 内容 |
|---|---|
| 文档类型 | 设计规格（授权侧） |
| 编写日期 | 2026-10-11 |
| 解决的问题 | 等保三级「访问控制」e/f/g 的落地方式；平台与业务系统在授权上的分工；判定执行位置；Casbin 模型选型 |
| 前置约定 | 平台**只做认证不做授权**——本文不改变这条边界，而是把「访问控制」拆成几段，分别归位 |

---

## 0. 结论先行：四段分工

| 环节 | 放在哪 | 理由 |
|---|---|---|
| **① 策略定义**（有哪些权限点、有哪些角色、角色对应哪些权限、哪个接口需要哪个权限） | **业务系统代码里**（由 SDK 声明） | 这是业务语义，只有业务方自己知道 |
| **② 策略登记**（把定义上报平台，形成权限目录 / 角色目录 / 接口映射，版本化留档） | **平台** | 让策略在平台侧**可见、可审计**，满足等保"策略可查"的要求 |
| **③ 授权动作**（把角色绑定到用户） | **平台**，由**安全管理员人工操作** | 满足等保 e)"由**授权主体**配置"——必须是真人负责、可追溯 |
| **④ 判定执行**（某个请求到底放不放行） | **SDK，业务系统内本地判定** | 需要业务语义与细粒度（行级、密级），平台做不到 |

> **一句话**：代码是策略的**定义源**，平台是策略的**登记中心与授权入口**，判定在**业务侧本地**完成。

**这个分工恰好回应了之前那个矛盾**：等保要求"授权必须由授权主体显式配置"，而产品定位是"不做授权"。拆开后就都成立了——平台提供**授权入口与审计**（不定义策略），业务方提供**策略定义与判定**。

## 1. 为什么这么分（对齐等保三级 e/f/g 逐条）

### e) 应由授权主体配置访问控制策略

- **"授权主体"是"人"**——被授权做这件事的管理员（通常是三员里的安全管理员），不是代码。
- 落地：平台提供**角色 → 用户**的绑定界面，安全管理员操作，每次绑定记录"谁、何时、把哪个角色给了谁"。
- **一个必须处理的细节**：策略的**定义**在代码里，那"策略"还算被"配置"了吗？
  → 解法就是第 ② 段：**注册上报**让平台持有一份**策略快照**（权限目录 + 角色目录 + 接口映射，带版本），测评时能出示"策略清单 + 变更历史"。
  **定义源在代码，登记与审计在平台。**

### f) 粒度达主体为用户级或进程级，客体为文件、数据库表级

先纠正一个常见误解（**这很关键**）：

> **RBAC 本身没有粒度上限。** 粒度取决于你把"资源"定义成什么——定义成"订单模块"就是模块级，定义成 `orders` 表就是表级，定义成 `orders.amount` 字段就是字段级。
>
> **RBAC 真正做不到的不是"表级"，而是"行级 / 数据实例级"**——比如"用户只能看到自己的订单"。因为 RBAC 只认角色，不认数据本身的属性。

所以 f) 的落地是分层的（见 §3 选型表）。

### g) 应对重要主体和客体设置安全标记，并控制主体对有安全标记信息资源的访问

"安全标记"就是**给主体和客体各打一个密级标签**，规则是"主体密级 ≥ 客体密级才可访问"。

**注意条文强度**：三级只要求"标记 + 按标记控制"；**只有四级才明确写"强制访问控制"**。

## 2. SDK 侧声明什么、上报什么

### 2.1 SDK 用起来长什么样（Java 示意）

**三段：声明模型 → 保护接口 → 行级 / 列表过滤。上报是启动时 SDK 自动完成的，业务方不写上报代码。**

```java
// ── ① 声明权限模型：一个 Bean，启动时 SDK 自动上报给平台 ──
@Configuration
public class AuthzConfig {
    @Bean
    public AuthzModel authzModel() {
        return AuthzModel.builder()
            .role("order_admin") .can("orders", "read", "write")
            .role("order_viewer").can("orders", "read")
            .role("auditor")     .can("orders", "read")              // 名为 auditor 的角色自动获得跨行级豁免
            .defaultRole("user") .can("profile", "read", "write")    // 默认角色：权限尽量小（见 §4）
            .build();
    }
}
```

```java
// ── ② 保护接口：一行注解 ──
@RequirePermission(resource = "orders", action = "read")
@GetMapping("/orders/{id}")
public Order get(@PathVariable String id) {
    Order o = orderService.get(id);
    Authz.checkRow(o.getUserId());       // 行级：只能看自己的（auditor 豁免）
    return o;
}

@RequirePermission(resource = "orders", action = "write")
@PostMapping("/orders")
public Order create(@RequestBody OrderReq req) {
    return orderService.create(req);
}
```

```java
// ── ③ 列表查询：自动注入过滤条件，避免"查出全量再过滤" ──
@RequirePermission(resource = "orders", action = "read")
@GetMapping("/orders")
public List<Order> list() {
    // 受限角色 → 自动变成 AND user_id = :me；order_admin → 不加过滤
    return orderRepo.findAll(Authz.scope("orders"));
}
```

**业务方需要掌握的东西只有三样**：一个 Builder（声明角色）、一个注解（保护接口）、两个方法（`checkRow` / `scope`）。

**加密级只是多一次方法调用**——`Authz.checkLabel(o.getLabel())`，**不需要换模型、不需要改配置**。这正是"一个 model.conf 逐层生效"带来的效果。

**为什么必须提供 `scope` 这一层**：如果只在"取出数据之后"做行级判定，列表接口就会**先查出全量、再逐条过滤**——既浪费性能，又有泄露风险（任何一处漏判就等于泄露）。**行级权限的正确做法是把过滤条件下推到查询。**


### 2.2 哪些是声明式、哪些由平台配置

这是最容易含混的一点，先把它拆清楚：

| 机制 | 由谁定义 | 放在哪 | 平台管什么 |
|---|---|---|---|
| **RBAC：角色 → 权限** | 开发者声明 | **代码** | **用户 → 角色 的绑定** |
| **Resource role：资源分组** | 开发者声明 | **代码** | 不管 |
| **客体密级：资源打标** | 开发者声明（数据分级结果） | **代码 / 配置** | 可选：登记与展示 |
| **主体密级：用户能看多高** | **从角色推导** | 代码 | 仍是"用户 → 角色"的绑定，**不需要单独配一份密级** |

**几个需要纠正的理解**：

1. **Resource role 不是"每个用户的东西"**，它是**资源的分组结构**——比如 `orders` 与 `order_items` 同属 `order_domain` 资源组，给资源组授权就等于给这两张表授权。它是**系统结构**，所以由开发者在代码里声明，**不需要平台配置、也不需要回传**。（它的价值是"降维"：避免给每张表单独授权。）

2. **密级确实需要数据驱动，但驱动它的是"角色"而不是"另一份配置"**：
   - **客体密级**（`orders` 表是"内部"）→ 数据分级的结果，声明式；
   - **主体密级**（这个用户能看多高）→ **可以用角色推导**：`secret_reader` 角色 → 密级"秘密"、`internal_user` 角色 → 密级"内部"。
   - 这样平台**不需要额外维护一份"用户密级表"**——它管好"用户 → 角色"这一件事就够了。

**结论**：

> **平台回传给业务系统的只有一样东西——用户的角色列表。其余全是代码里的声明。**
>
> 这不是简化，而是把"业务语义"和"授权事实"正确分开：**角色与权限的映射是业务语义（代码），用户与角色的绑定是授权事实（平台）。**

### 2.3 注册上报（启动时 + 变更时）

| 上报内容 | 用途 |
|---|---|
| 权限点目录 | 平台的权限清单 |
| 角色目录（角色 → 权限） | 安全管理员绑定角色时的参考；策略快照 |
| 接口 → 权限映射 | 策略快照；便于排查"这个接口谁能访问" |
| 默认角色声明 | 登记默认放行范围，供审计 |
| 数据敏感标记定义（若用 BLP） | 密级目录 |

平台把每次上报存成**带版本的策略快照**，可对比、可回溯。

## 3. Casbin 模型选型

Casbin 是 PERM 元模型（Policy / Effect / Request / Matchers），**模型可组合**——这是它最大的价值：可以在同一个 `model.conf` 里同时用 RBAC 的 `g` 和 ABAC 的属性访问。

### 3.1 内置模型与等保要求的对照

| 等保要求 | 需要的粒度 | 对应 Casbin 模型 | 说明 |
|---|---|---|---|
| **e) 授权主体配置策略** | — | 任意模型 | 平台管"角色→用户"绑定；Casbin 管"角色→权限"判定 |
| **f) 表级 / 资源级** | 客体 = 数据库表、接口资源 | **RBAC with resource roles**（`rbac_with_resource_roles_model.conf`） | 资源就是表名或资源组名。表很多时叠 **RBAC with pattern**（KeyMatch）降维，避免策略条目爆炸 |
| **f) 行级 / 数据实例级** | "只能看自己的订单" | **ABAC**（`abac_model.conf`，用 `resource.Owner` 这类属性）或 **ReBAC**（`rebac_model.conf`，按关系判定） | **RBAC 做不到**——它只认角色，不认数据属性 |
| **g) 安全标记（密级）** | 主体密级 vs 客体密级 | **BLP**（`blp_model.conf`）✅ | **你的猜测正确：Bell-LaPadula 是 Casbin 的内置模型。** 若要同时管完整性，用 **LBAC**（`lbac_model.conf`，格模型，机密性与完整性统一） |
| 上下文条件（IP / 时间） | — | **IP Match**（`ipmatch_model.conf`）、PBAC、RBAC with time constraints | |
| 拒绝优先 / 优先级 | — | **Deny-override**（`rbac_with_deny_model.conf`）、**Priority**（`priority_model.conf`） | 黑名单与例外场景 |
| **文件级** | OS 文件 | **无可用模型** | 应用层库管不到操作系统文件——**必须由主机 / OS 加固层承担** |

### 3.2 推荐组合

**`RBAC with resource roles`（表级底座）+ `ABAC`（行级）+ `BLP`（密级）**，用 Casbin 的多模型组合能力写进同一个 `model.conf`。

示意（**语法仅作示意，实现时以 Casbin 官方文档为准**）：

```ini
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
# RBAC：角色 → 资源 → 动作（表级）
m = g(r.sub, p.sub) && r.obj.name == p.obj && r.act == p.act
    # BLP：主体密级不低于客体密级（g 条）
    && r.sub.clearance >= r.obj.label
    # ABAC：行级归属，或审计员例外
    && (r.obj.owner == r.sub || g(r.sub, "auditor"))
```

### 3.3 三处必须说清的边界

1. **文件级不在任何应用层模型的能力范围内**——这一条只能写进「访问控制责任划界声明」，交给主机 / OS 加固层。不写清就会在测评时被判缺项。
2. **BLP 解决的是"密级"，不是"角色"**——两者是叠加关系，不是替代关系。角色管"业务上能不能做"，密级管"这个数据等级够不够"。
3. **密级标签本身也是数据**——它需要被保护（防止被篡改拉低），这与平台侧「关键数据存储完整性」是同一条要求。

---

### 3.4 选型结论：组合，而不是单选

**不是"选一个"，也不是"实现几个互斥的模型"，而是——一个可组合的底座 + 几档预置模板 + 允许自定义。**

三条理由：

1. **关津自身几乎不需要授权模型**——它只有几个管理员角色，用最简 RBAC 就够。**权限模型的主战场在 SDK 侧**。
2. **SDK 面对的是 100 个需求各异的业务系统**。硬编码一种模型反而限制它们。
3. **Casbin 的 PERM 元模型本来就是为"组合"设计的**——RBAC 的 `g()` 与 ABAC 的属性访问可以写进同一个 matcher（见 §3.2 示意）。

#### 内置哪些、不内置哪些

| 模型 | 是否内置 | 理由 |
|---|---|---|
| **RBAC with resource roles** | ✅ **默认** | 覆盖绝大多数业务系统（"100 个系统里 90 个是这么玩的"）；表级粒度够用 |
| **ABAC** | ✅ 可选 | **行级 / 数据实例级的唯一解** |
| **BLP** | ✅ 可选 | **等保 g) 密级要求的唯一解**（Casbin 内置模型） |
| Deny-override / Priority | ✅ 作为**修饰符** | 与主模型正交，可按需叠加 |
| RESTful(KeyMatch) / IP Match | ✅ 作为 **matcher 函数** | 是匹配器不是模型 |
| ReBAC | ❌ 不内置 | 适用于"文档协作"这类关系型场景，对 100 个业务系统属特例；业务方可自行写 `model.conf` 扩展 |
| LBAC / Biba | ❌ 不内置 | LBAC 是 BLP 的超集（多了完整性维度）、Biba 是完整性专用——本场景用不到 |
| OrBAC / UCON / PBAC | ❌ 不内置 | 学术味重，业务价值低 |

#### 怎么落地：**一个** model.conf，三层能力逐层自动生效

先澄清一个容易误解的点：**不是三个 model.conf 并行跑，也不需要 SDK 里放三套。**

**正确做法是只有一个 `model.conf`**，三层能力**按"策略里有没有声明该属性"逐层自动生效**：

| 策略里写什么 | 实际生效的能力 |
|---|---|
| 只写 `p, role, orders, read` | **基础 RBAC**（表级 / 资源级） |
| 资源再带上 `owner` 属性 | 自动叠加**行级判定**（ABAC） |
| 资源再带上 `label` 属性 | 自动叠加**密级判定**（BLP） |

matcher 示意（**语法仅示意，实现时需以 Casbin 官方文档为准并实测**）：

```ini
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
# 底座：角色 → 资源 → 动作（RBAC）
m = g(r.sub, p.sub) && r.obj.name == p.obj && r.act == p.act
    # 资源声明了 owner → 启用行级判定；未声明则跳过
    && (r.obj.owner == "" || r.obj.owner == r.sub || g(r.sub, "auditor"))
    # 资源声明了 label → 启用密级判定；未声明则跳过
    && (r.obj.label == "" || r.sub.clearance >= r.obj.label)
```

**为什么这样比"三档模板"更好**：

| 理由 | 说明 |
|---|---|
| 业务方**零配置** | 不需要理解"我该选哪一档模板"——这本身就违反"接入面只 5 个概念"的约束 |
| 升级只需加一个属性 | 要行级就多写 `owner`，要密级就多写 `label`，**不用换模型、不用改代码** |
| 只有一个 Enforcer、一套策略 | 心智与运维成本最低；不存在"选错模板"这类误配 |

**唯一要注意的实现细节**：`r.obj` 需要是一个**结构体**（含 `name` / `owner` / `label` 三个字段），RBAC 场景只填 `name`、其余留空字符串。这正是 Casbin ABAC 的标准用法（通过 `r.obj.Field` 访问属性）。

**一个业务系统只用一套模型**——不鼓励"同一系统内不同接口跑不同模型"，那会让策略管理变得难以理解。

> **一条不做的**：SDK 不提供"跨业务系统的统一角色模型"。100 个系统各自定义角色，平台只做登记与绑定——强行统一就是"授权复杂度无限"那个陷阱。

---

### 3.5 能不能混用不同模型

**技术上能。** Casbin 支持在一个进程里创建多个 Enforcer，各绑各的 model——所以"接口 A 用模型 1、接口 B 用模型 2"是能跑起来的。

**但我们的设计里不需要，也不建议**：

| 理由 | 说明 |
|---|---|
| **我们的模型已经够用** | 一个 `model.conf` 通过"属性是否声明"就能覆盖 RBAC / 行级 / 密级三种需求，**根本没有混用的必要** |
| **混用会带来隐蔽风险** | 开发者得记住"这个接口用的是哪个模型"；一旦记错，权限会**静默失效或静默放宽**——这类 bug 很难在测试里被发现 |
| **策略数据会分裂** | 两套模型往往需要两套策略数据与两个命名空间，运维复杂度翻倍 |

**唯一的例外**：如果确实要接入 Casbin 的其他模型（例如某个系统真的需要 ReBAC 做关系型判定），那就用**第二个 Enforcer**——但必须**严格隔离**：独立的 model、独立的策略命名空间，并在文档里明确标注哪些接口用哪一套。

## 4. 默认角色

**为什么必须有**：用户没有被绑定任何角色时，业务系统会拒绝一切请求 → 系统不可用。

**设计原则**：

| 原则 | 说明 |
|---|---|
| **角色名与权限点由接入方把控** | 平台**不预设**任何具体角色名与权限点。接入方通过 `AuthzModel.builder().defaultRole(name).can(...)` 自行声明，随策略快照上报——平台只负责**登记与审计**，不负责定义 |
| **权限尽量小** | 默认角色只覆盖"公开接口"和"我的数据"。**不做成"已登录即可访问全部"**——那会被测评方视为"默认放行"，直接违反 e) |
| 显式声明、上报留档 | 默认角色也是权限，必须在注册时上报，进入策略快照 |
| 只兜底合成角色 | 默认角色是"合成角色"（如 `authenticated_user`），不是业务角色；业务角色仍由安全管理员逐个绑定 |

## 5. 角色绑定如何到达判定点

判定在 SDK 侧，所以 SDK 必须知道"这个用户有哪些角色"。两个方案：

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A · 放进令牌**（推荐） | 令牌 claim 里带 `roles: [...]`；SDK 读角色 + 用本地代码里的"角色→权限"定义判定 | **零回源**，判定纯本地，延迟为零 | 令牌变大（角色多时）；角色变更要等令牌过期 |
| B · 平台下发 + SDK 缓存 | SDK 拉取"用户→角色"绑定并缓存（同 JWKS 模式） | 令牌小 | 需要缓存与失效机制，又多一套增量同步 |

**推荐 A**，并配一条策略解决"角色变更延迟"：

> **角色变更时，平台主动撤销该用户会话**——用户重新登录后拿到新角色。
> 因为平台已承载数据面，撤销是**实时生效**的（见规划 §7.1），所以"改了角色立刻生效"成立。
> 代价是用户要重新登录一次——但角色变更是低频事件，这个代价可接受。

## 6. 边界（平台做什么、不做什么）

| 平台做 | 平台不做 |
|---|---|
| 接收并保存策略快照（权限 / 角色 / 接口映射） | **不定义**权限点与角色（业务语义） |
| 提供角色目录的可视化与检索 | **不定义**判定逻辑 |
| 提供"角色 → 用户"绑定界面与审计 | **不替业务做**行级 / 密级判定 |
| 把角色写进令牌 | **不承担**文件级访问控制（主机层） |
| 角色变更时撤销会话 | **不做**跨业务系统的统一角色模型 |

最后一条尤其重要：**平台不做"统一角色模型"**。100 个业务系统的角色体系各不相同，强行统一就是"授权复杂度无限"那个陷阱。平台只提供**登记、绑定、下发、审计**这套机制。
