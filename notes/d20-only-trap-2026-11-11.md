# D20 索引迁移：`ONLY` 静默失效的坑 + 断言位置（2026-11-11）

Gate 用真 PG 17.11（144 万行 / 13 个存活分区）跑出对照：链尾读 711.6ms → **0.96ms**、
`TailTagBefore` 829ms（首跑 1235ms）→ **1.22ms**、审计写 p99 **450.63ms → 4.30ms**。
同批指出一个会让迁移"看起来成功但其实无效"的坑，本文把它钉进迁移与本仓断言。

## 坑：`CREATE INDEX … ON ONLY` 只建父索引

`ON ONLY audit_logs` 只在**父表**建索引条目，**现有分区没有、将来新分区也不继承**；
`migrate up` 照样报 success（golang-migrate 只判 SQL 有没有报错），但计划仍是 `Seq Scan + Sort`
——"索引加了等于没加"，只有压测/线上慢查询才会暴露。

本仓迁移**没有**写 `ONLY`：

```sql
CREATE INDEX audit_logs_created_id_idx ON audit_logs (created_at, id);   -- 000021，无 ONLY
```

⚠️ 一个容易误判的地方：`pg_indexes.indexdef` 对**分区表的父索引**天然显示为
`ON ONLY public.audit_logs`（父索引只是模板条目）——**那不是写了 `ONLY`**。

## 真正的判据：子索引数 == 分区数（已写成可执行断言）

`internal/store/audit_created_id_idx_db_test.go::TestDBAuditCreatedIDIndexOnParentAndEveryPartition`：

1. 父索引存在且 `relkind='I'`（分区父索引）；
2. **每个现有分区**都挂着父索引的子索引（按 `pg_inherits` 父子关系判，不按名字——
   PG 给分区建的子索引叫 `audit_logs_pYYYYMM_created_at_id_idx`）；
3. 形状 `btree (created_at, id)`，无 `DESC` / 无 `WHERE`(partial) / 非 `UNIQUE`；
4. `audit.EnsurePartitions` 建一个"两年后"的新分区 → 立刻断言它也自动继承。

这三条一起把"ONLY 静默失效"堵在 CI 里（索引缺失/分区漏建/新分区不继承，任一即红）。

## `down` / `up` 幂等（本地实跑，独立新库）

```
up    → version=21，子索引数 3 == 分区数 3
down1 → version=20，pg_indexes 里 `*_created_at_id_idx` 命中 0（父+子索引一起消失）
up2   → version=21，子索引数回到 3（幂等）
```

CI 侧同款整链往返在 `scripts/verify-migrate-roundtrip.sh`（`up(21) → down(nil, 残留 0) → up(21, 快照一致) → down(nil)`）。

## 关于 Gate 的 `generated/d20/check-plan.sh`

那个脚本在 Gate 自己的工作区，**没有进仓**，所以 CI 里引用不到。我的判断：

- **结构性前置**（索引在父表 + 每个分区 + 新分区继承 + 形状）已经由上面的集成用例守住——
  这正是"ONLY 静默失效"的**唯一**入口，守住它就不会退化。
- **计划形状断言**（0 个 `Seq Scan`、0 个 `Sort (`、必须有 `Merge Append` + `Index Scan Backward`）
  需要 ≥10 万行才有意义（空表会假绿），放进主闸会让每个 job 多跑一份大数据夹具；
  建议由 Gate 把它落到 `scripts/check-audit-plan.sh`（带 `MIN_ROWS` 门槛与 `--expect=unindexed` 负控），
  挂在 CI 的**独立 report-only step** 或发布前检查里，而不是混进三闸。
- 在那之前：每次动 `audit_logs` 的索引/查询，手工跑一次上面那段 `EXPLAIN (ANALYZE, BUFFERS)` 对照，
  把前后数值贴进 PR。
