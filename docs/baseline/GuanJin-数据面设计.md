## 0. 结论先行

| # | 结论 |
|---|---|
| 1 | **关津数据面 = 一个「带认证语义的路由器」，不是通用网关。** 通用的网关能力（TLS 终结、负载均衡、WAF、灰度、熔断…）**全部剥给成熟组件**，剥完之后自己只剩 **7 件事** |
| 2 | 推荐形态：**前置 Nginx/Kong（TLS 终结 + 粗路由 + WAF）→ 关津数据面（认证 / 会话 / 撤销 / 身份注入）→ 业务系统**；后置网关可选 |
| 3 | 服务间通信实体鉴别：**优先 mTLS**（对开发者零成本），备选 HMAC 签名（对运维零成本） |

## 1. 剥离清单

### 1.1 必须 关津自己做的（剥完后剩下的全部）

| # | 能力 | 为什么剥不掉 |
|---|---|---|
| 1 | **令牌验签与认证** | 需要签名密钥与认证语义，只有平台有 |
| 2 | **会话管理 + 实时撤销** | 需要会话状态；撤销必须与"谁是谁"绑定 |
| 3 | **身份注入**（把用户标识 / 角色 / 保证级别传给下游） | 只有它知道"这个用户是谁" |
| 4 | **按业务系统的差异化策略**（不同 client 不同的认证要求、档位） | 只有它知道 client 的档位 |
| 5 | **认证风控**（账号级失败锁定、异常检测、图形验证码触发） | 跨业务系统的账号级状态在它手里 |
| 6 | **认证审计** | 合规要求，且只有它知道认证结果与因子组合 |
| 7 | **单点登出通知** | 需要会话与其他业务系统的映射关系 |

**一句话**：这 7 件事的共同特征是——**都依赖"认证语义"**。它们必须知道「这个请求属于哪个业务系统」「这个用户是谁」「这个会话还有效吗」。通用的前置/后置组件不具备这些语义。

### 1.2 可前置给成熟组件（Nginx / Kong / 云 LB）

| 能力 | 说明 |
|---|---|
| **TLS 终结** | 前置组件终结 TLS，向内明文（或再加密）。关津只看明文，省掉证书与握手开销 |
| **四层负载均衡** | 外部 LB / LVS / 云 LB |
| **主机名 / 路径粗路由** | 把流量分流到 关津（例如只把需要认证的域送进来） |
| **WAF** | 专用 WAF 或前置网关的 WAF 模块 |
| **DDoS 防护 / IP 黑名单** | 网络层能力 |
| **通用限流**（按 IP / 总 QPS） | 与"账号级"限流不同，这是无状态的粗限流 |
| **静态资源缓存 / CDN** | 登录页静态资源可直接走 CDN |

### 1.3 可后置给成熟组件（可选）

| 能力 | 说明 |
|---|---|
| 业务路由（按 service 名转发） | 业务系统数量大、路由复杂时才需要 |
| 服务发现 | 与 K8s / Consul / Nacos 集成 |
| 熔断 / 降级 / 重试 | 成熟网关的强项 |
| 协议转换（gRPC / WebSocket） | |
| 灰度 / 权重路由 | |
| 响应缓存 | |

> ⚠️ 后置网关是**可选的**。如果 100 个业务系统的路由不复杂，关津自己转发即可——少一跳、少一个运维点。**先不引入，等真的复杂了再说。**

### 1.4 可完全外部化

CDN、专用 WAF、硬件负载均衡、DDoS 清洗——这些本来就不该由应用承担。

## 2. 推荐分层

```text
客户端
  ↓
[前置 Nginx / Kong]     TLS 终结 · 粗路由 · WAF · 通用限流 · DDoS 防护
  ↓  （内网；如需可再加密）
[关津数据面]          认证 · 会话 · 实时撤销 · 身份注入 · 按 client 策略 · 认证风控 · 认证审计
  ↓
[后置网关 —— 可选]      业务路由 · 服务发现 · 熔断 · 协议转换
  ↓
业务系统
```

**这个形态的关键性质**：

| 性质 | 说明 |
|---|---|
| **撤销实时生效** | 请求都经过 关津 → 撤销判定即时，不存在"拉取间隔" |
| **可用性风险从"局部"升为"全局"** | 数据面故障 = 全部业务系统不可用。这是合并形态的固有代价，必须用冗余部署对冲 |
| **关津是薄的一层** | 剥掉通用网关能力后，它的逻辑量远小于一个通用网关；但它**站在流量路径上**，所以性能和稳定性要求反而是全局最高的 |

---

## 3. 为什么这 7 件事剥离不掉

反证法：如果把它们交给前置/后置组件做，会怎样？

| 交给前置组件 | 后果 |
|---|---|
| 让它验签 | 它需要签名公钥 → 它就变成了第二个认证点 → 撤销、会话、审计都要在它那里再做一遍 → **等于把 关津复制了一份** |
| 让它做按 client 的策略 | 它需要知道每个 client 的档位与策略 → 策略变更要同步到它 → 又多一条同步链路 |
| 让它做认证风控 | 它需要跨业务系统的账号级状态 → 要连 Redis / 调用平台接口 → **又回到"每个请求回源"** |
| 让它写认证审计 | 它需要知道认证结果与因子组合 → 那是认证语义 |

**结论**：这 7 件事只要交出去一件，就会牵出其他六件。所以它们是**不可分割的一组**。

## 4. 服务间通信实体鉴别（密评 8.2 a)）

> 先明确：**设备指纹放 header 不算**。请求头是客户端自填的字符串，攻击者可改，没有密码学绑定就等于没有认证；靠"内网隔离"或"来源 IP 白名单"同样不算。条文关键词是"**密码技术**"。

### 4.1 三种做法对比

不要只比 mTLS 和 HMAC——**签名其实有两种形式，差别很大**：

| 维度 | mTLS（双向证书） | HMAC（共享密钥签名） | **非对称签名（私钥签 / 公钥验）** |
|---|---|---|---|
| 密钥分发 | 要 CA，各方持证书 | 要**把密钥发给每一方** | **只分发公钥**（可像 JWKS 一样公开） |
| 泄露后果 | 单证书泄露只影响那一方 | **共享密钥泄露 = 双方都能伪造，且一破全破** | 私钥泄露才受影响；公钥泄露无害 |
| 防抵赖 | 有 | **无**（双方都能签，说不清是谁签的） | **有** |
| 换密钥 | 证书轮换 + 吊销（CRL/OCSP） | 换密钥要**通知所有持有方** | **只换自家私钥 + 公布新公钥**，各方自动跟上 |
| 防重放 | TLS 会话天然保证 | 需 timestamp + nonce（有状态） | 需 timestamp + nonce（有状态） |
| 国内对接生态 | 低（少见） | **高**——微信 / 支付宝 / 银联 / 银行都是这套 | 中高（本质也是"密钥 + 签名"，只是换成密钥对） |
| 开发者成本 | 低（改客户端配置） | 中（接验签逻辑） | 中（接验签逻辑，**但可与验 JWT 复用同一套代码**） |
| 基础设施依赖 | CA 体系（或有服务网格自动签发） | 无 | **无**（可复用已有的 JWKS 发布机制） |

### 4.2 "每个请求用 key 算一下"漏掉的三件事

HMAC 的**计算**确实简单，但完整实现要处理：

1. **密钥的分发与轮换**——100 个业务系统各一份密钥？还是共用一份？共用则一破全破；各一份则要管理 100 份的分发与轮换，且不能明文落配置（这又回到"密钥外部注入"那条底线）。
2. **时钟同步**——`timestamp` 偏差容忍要配置；容器 / 虚拟机 NTP 不可靠时会出现"签名永远过期"这类难排查的故障。
3. **nonce 的状态**——防重放需要记录"有效窗口内已用过的 nonce"，这是一个有状态的组件（落 Redis），且窗口大小要权衡（窗口越大越安全，内存占用越高）。

**这三件事 mTLS 都不用做**（TLS 会话自己处理）。

### 4.3 先澄清一件事：mTLS 用在哪条链路上

这是最容易搞错的地方——**mTLS 是给「服务 ↔ 服务」用的，不是给浏览器用的。**

| 链路 | 需要 mTLS 吗 | 说明 |
|---|---|---|
| **浏览器 → 关津** | ❌ **不需要** | 浏览器**技术上支持** mTLS（会弹证书选择框），但**C 端用户手里没有客户端证书**——这不是技术限制，是事实限制。而且密评 8.2 a) 本来就不要求对终端用户做 mTLS；终端用户的鉴别属于 **8.4 a)**，用口令 / 动态口令解决。这一段普通单向 TLS 即可。 |
| **关津 → 业务系统**（转发请求） | ✅ 需要 | 这是"通信实体"。业务系统要能确认"这个请求真的来自 关津"。 |
| **业务系统 → 关津**（注册上报、拉取策略） | ✅ 需要 | 平台要能确认"你是哪个业务系统"。 |
| **关津 → 数据库 / Redis** | ✅ 需要 | 用 TLS + 网络隔离 / 内网凭证。 |

**所以"mTLS 需不需要客户端配置"这个问题要分对象**：需要配置的是**服务端程序**（关津自己的代码、SDK），**不是浏览器、也不是终端用户**。

### 4.4 前置 CDN / ESA / Cloudflare 能解决多少

你的直觉**对了一半**——对齐一下具体是哪一半：

| 链路 | 谁覆盖 | 用什么 |
|---|---|---|
| 终端用户 → 前置节点 | 前置产品自带 | 单向 TLS（服务端证书） |
| **前置节点 → 关津源站** | ✅ **前置产品覆盖，且用的就是 mTLS** | **回源鉴权**——Cloudflare 叫 Authenticated Origin Pulls，ESA 有对应的源站认证：源站验证"请求确实来自该边缘网络"的客户端证书 |
| **关津 → 业务系统**（内网） | ❌ **前置产品管不到** | 关津自己做（mTLS 或 HMAC 签名） |
| **关津 → DB / Redis**（内网） | ❌ 前置产品管不到 | 关津自己做 |

**结论**：
- **前置 ESA / Cloudflare 确实解决了"边缘 ↔ 源站"那一段**，而且用的就是 mTLS——这部分可以直接划掉，不用自己实现。
- **但内网服务间那几段在它的视野之外**，仍然要自己做。
- 而且注意：**不要为了让前置产品管这一段而把内网调用绕出去走公网边缘**——那是把内网流量推到公网，得不偿失。

### 4.5 推荐（本轮修正）

**修正说明**：此前建议"优先 mTLS"，理由不够充分。在**系统间调用 / 对外对接**这个场景下，**应用层签名才是国内的正道**——微信 / 支付宝 / 银联 / 银行开放平台全是"密钥 + 签名"，对接方熟悉、不需要教对方配证书、不依赖 CA 基础设施。mTLS 真正低成本的前提是**服务网格自动签发轮换证书**（Istio / Linkerd 的标配），手工管证书则成本和扯皮风险都不低。

| 场景 | 推荐 | 理由 |
|---|---|---|
| **关津 → 业务系统**（转发 + 身份注入） | **非对称签名**（关津私钥签、业务系统公钥验） | 见下方"为什么这一个方案同时解决两件事" |
| **业务系统 → 关津**（注册上报、拉策略） | **HMAC，每业务系统一个独立 secret** | 这是"对接"语义，密钥是通行做法；**不要共用一个** |
| **边缘 ↔ 源站** | 前置 CDN / ESA 的**回源鉴权**（开箱即 mTLS） | 零研发成本，直接白拿 |
| 已有服务网格的内部环境 | mTLS 交给网格自动处理 | 证书生命周期自动化后，mTLS 反而是最省事的 |

#### 为什么"非对称签名"这一个方案同时解决两件事

**关津是网关，转发时必须在 header 里注入用户身份**（否则业务系统不知道请求是谁的）。但——

> **那个 header 必须被签名。** 如果只是塞一个 `X-User-Id: 123` 而不签名，任何能访问到业务系统的人都可伪造。**所以签名不是额外引入的负担，而是本来就该做对的事。**

而一旦做了签名，密评 **8.2 a)「通信实体身份鉴别」顺带就满足了**——因为签名里同时包含：

- **系统标识 + 时间戳** → 业务系统据此确认"请求确实来自 关津"（这就是通信实体鉴别）
- **用户身份 + 角色 + 保证级别** → 这就是身份注入

也就是**一次签名，两件交付**。

再加两个好处：
- **公钥可以复用 JWKS 那套发布机制**——业务系统验签的逻辑与验 JWT 完全一致，零新增依赖；
- **不用给 100 个业务系统分发密钥**——只需公布公钥。

### 4.6 网关向业务系统传递什么

**只塞一个 header——一个签名的内部令牌。**

```http
X-GuanJin-Assertion: <JWT>
```

**为什么不塞多个明文 header**（比如 `X-GuanJin-User-Id: 123`、`X-GuanJin-Roles: order_admin`）：

> 明文 header 的最大风险是**业务系统可能忘了验签就直接用**——那就等于任何能访问到业务系统的人都能伪造身份。**把信息放进签名内部，不解签名就读不到，从机制上强制验签。**

**内部令牌的 claim**：

```json
{
  "iss":  "guanjin-gateway",
  "sub":  "u_12345",
  "aud":  "order-service",
  "cid":  "order-portal",
  "uname":"zhangsan",
  "roles":["order_admin"],
  "acr":  "AAL2",
  "amr":  ["pwd", "otp"],
  "iat":  1730000000,
  "exp":  1730000060,
  "jti":  "..."
}
```

**几个关键性质**：

| 性质 | 说明 |
|---|---|
| **逐请求签发** | 它不像用户令牌那样长期存在——它是网关**每个请求现签**的 |
| **有效期极短**（如 60 秒） | 只作为**防重放窗口**，不是会话生命周期 |
| 不需要刷新 | 每个请求重新签，没有续期概念 |
| **独立密钥对** | 与用户令牌的密钥分开（用途分离）；但同样通过 JWKS 发布、用 `kid` 区分 → **业务系统验签代码可直接复用** |

**SDK 侧要做的事（5 步）**：

1. 拦截请求，读 `X-GuanJin-Assertion`；
2. **验签**——失败直接 401；
3. 校验 `exp`，并用 `jti` 做重放检测；
4. 把 claim 放进请求上下文，供 `Authz.*` 使用；
5. ⚠️ **在转发给下游之前剥离该 header**——否则内部令牌会被透传到更深的下游，或被日志记录下来。

### 4.7 算法选择

用户在上一轮建议"应用级密钥 + 签名搞定，选个符合最高等级的"。方向对，但**"密钥"要分清是哪一种**——两种签名的运维代价是相反的：

| | **SM2 签名（非对称）** | **HMAC-SM3（对称）** |
|---|---|---|
| 密钥管理 | **1 对密钥**，公钥公开（复用 JWKS 发布） | 每个验签方一份密钥 → 100 个业务系统要 100 份分发与轮换；若共用则一破全破 |
| 防抵赖 | 有 | 无 |
| 性能 | 每请求一次签名，约 **0.3 ~ 1 ms**（Java + BouncyCastle，**需实测**） | **微秒级**，可忽略 |
| 高 QPS 下的影响 | 显著——需要按核数扩容（现代服务器 16~32 核可承受，且数据面本就多副本，开销可水平分摊） | 无感 |
| 合规 | 非对称国密，密评最直接 | 对称国密，也是密码技术，合规 |

**推荐：SM2 签名。** 理由是在"**一方签、多方验**"（关津向 100 个业务系统签名）这个拓扑下，**非对称的密钥管理优势压倒性能劣势**——只需维护一对密钥、公布一次公钥；而 HMAC 要为每一方管理密钥。

**但有两个前提必须落实**：

1. **必须实测签名性能**——它落在每个请求上。若成为瓶颈，退化到 HMAC-SM3（代价是密钥管理变复杂）。
2. **签名算法要留出可替换的抽象**——不要把它写死，因为这条路径的性能表现会决定最终选型。

⚠️ 别混淆：之前讨论的"省掉 client_secret、改用 PKCE"是**授权码换令牌**场景的事，与"通信实体身份鉴别"不是一回事，不能相互替代。

## 5. 可行性判断（不做计划，只看有没有硬伤）

| 维度 | 判断 |
|---|---|
| **工程量** | ✅ 剥掉通用网关能力后，数据面逻辑量可控——本质是一个"带认证钩子的反向代理"。Go 的标准库 `net/http/httputil.ReverseProxy` 已提供基础能力，主要工作在于连接池、超时、背压与认证钩子 |
| **性能** | ⚠️ 需要认真做：站在流量路径上意味着它承受全量 QPS。**这是本项目性能压力最大的模块**，与"认证服务"（低频）完全不同量级 |
| **稳定性** | ⚠️ **最大风险**。数据面故障 = 全局不可用；而自研组件的成熟度天然低于成熟网关。缓解方向：把数据面做到极薄（少功能 = 少故障面）+ 冗余部署 |
| **长期维护** | ⚠️ 通用网关的演进（新协议、新攻击面）会变成自己的责任。**这就是"剥离通用能力"的价值——剥得越干净，长期维护成本越低** |
| **合规** | ✅ 剥离后反而更清晰：关津承担认证语义相关部分，TLS / WAF / DDoS 由专业组件承担，责任边界更容易写清楚 |

**一句话可行性结论**：**技术上没有硬伤，但有两条必须正视的代价**——(1) 数据面会成为全局可用性的单点，必须冗余；(2) 站在流量路径上，性能要求比认证服务高一个数量级。这两条不是"能不能做"的问题，是"要做就按高可用系统来做"的问题。
