你是「关津（GuanJin）」项目的接手人。以下是你开始工作前必须知道全部背景、约束和现状。请先读完本文，再动手。

### 一、项目是什么

- 关津是一套面向 C 端的统一认证基础设施（IAM 中的「认证」部分），**单租户**、集团自建自运营。
- 目标规模：**100 个业务系统、千万级 C 端用户、峰值并发登录 200 QPS**；用户全部为 C 端，**开放自注册**。
- 它**只做认证**，不做授权、不做组织/人事、不做业务功能。这条边界是产品的生死线（见《GuanJin-产品核心定义.md》§1.5）。
- 名称取自《唐六典·刑部》：关为陆上关卡、津为渡口，古代于关津设吏查验行人凭证——平台之于 100 个业务系统，正是「进出必经、只做查验」的节点。设计文档中也称 SpIAM Next。
- 合规目标：**等保三级 + 密评**（密评目标等级与密码产品路径见 §七 待确认）。
- 与旧 SpIAM 的关系：旧 SpIAM 是给内部员工用的 OIDC 认证网关（已有可运行代码）；关津是 **greenfield 新项目**，只借鉴设计、不继承代码，落点为独立仓库（代号与仓库名尚未确定）。

### 三、已冻结的决定（不得擅自更改）

| 维度 | 决定 |
|---|---|
| 产品性质 | Greenfield、独立仓库；只借鉴旧设计，不继承代码 |
| 使用方 | 单租户；运营方为集团内部；用户全部是 C 端 |
| 规模 | 100 个业务系统 / 千万级用户 / 峰值并发登录 200 QPS |
| 账号来源 | 开放自注册；注册必带业务系统上下文，按目标系统的准入规则计算 |
| 因子 | V1 四类（密码 / 短信 / 邮箱 / TOTP）；类型不设限、架构上无限扩充 |
| 档位 | 只有「客户端档位」一层（访问该业务系统的准入门槛）；默认 L2，承诺 AAL1；要等保三级须显式选 L3；平台级实现全部按最高固定 |
| 无上下文判定 | 按该用户已访问过的业务系统中档位最高的那一个（「生效配置」） |
| 权限 | 平台不定义授权策略；平台管「用户→角色」绑定与审计，业务方管「角色→权限」定义；判定在 SDK 本地 |
| 数据面 | 关津承载数据面、代替独立网关；且为薄数据面——只做依赖认证语义的 7 件事，TLS 终结 / WAF / LB / 灰度 / 熔断前置给 nginx 或 Kong |
| 部署 | 多副本 + 无状态化；挑战落库，Redis 只承载限流计数与热缓存 |
| 撤销 | 承载数据面形态下实时生效，无需撤销清单传播 |
| 服务间认证 | 关津→业务系统用 SM2 非对称签名；业务系统→关津用每系统独立 secret 的 HMAC-SM3 |
| 身份注入 | 单个签名 header `X-GuanJin-Assertion`，逐请求签发、有效期极短、独立密钥对经 JWKS 发布；SDK 验签后必须剥离 |
| 用户令牌 | JWT（`SM3withSM2` 签名，含 `kid`）；`/userinfo` 本地解析；`/oauth/introspect` 仅限低频，禁止每请求校验 |
| 挑战 | 权威状态落 PostgreSQL `challenges` 表，Redis 只做限流与热缓存 |
| 密钥与算法 | 主密钥环境变量注入、不落库；PBKDF2-SM3、HMAC-SM3、SM4、SM3withSM2，均固定最高级 |
| 数据访问 | GORM + 五条硬约束（禁软删除、禁 AutoMigrate 上线、唯一冲突映射业务错误码、复杂查询走 Raw()、高频表批量写） |
| SDK | 只出 Spring Boot 2.x（javax）产物；拆 `guanjin-core`（零 Spring 依赖）+ `guanjin-spring-boot2`（适配层） |
| C 端个人中心 | 全量：改密、换绑、在线会话与踢设备、注销、数据导出 |

### 五、工程硬约束

- 后端：Go 1.25、`CGO_ENABLED=0`、Gin、GORM、golang-migrate、pgx、`tjfoc/gmsm`、`golang-jwt/v5`、zap、`caarlos0/env`。
- 前端：Vue 3.5 + Vite 8 + TypeScript + pinia + element-plus；产物 `go:embed` 与后端同端口。
- SDK：Java 17 + Spring Boot 2.7.18，`guanjin-core` 零 Spring 依赖，`guanjin-spring-boot2` 只做 javax 适配。
- Schema 唯一权威是 `migrations/`；**禁止 AutoMigrate 上线**；**禁止 GORM 软删除**（模型里不得出现 `gorm.DeletedAt`）。
- 无本地重要状态：挑战 / 会话权威状态落 PostgreSQL，Redis 只承载限流计数、热缓存、`jti` 防重放；多副本行为必须一致。
- **fail-closed**：Redis / DB / 密钥不可用时拒绝服务，绝不降级放行。
- 国密固定最高级、与档位无关：PBKDF2-SM3（迭代 ≥100000、盐 ≥16B）、SM3 摘要、审计 HMAC-SM3、敏感字段 SM4、网关断言 SM2、对外令牌 SM3withSM2；签名 / 摘要走可替换 SPI。
- 主密钥只从环境变量注入，不落库（`runtime_config` 的 CHECK 禁止）。
- 所有权限校验必须基于**权限码**，不得内置角色判断逻辑（平台只回传角色列表，判定在 SDK 本地）。
- **不允许隐性逻辑**：默认值、隐式回退、自动推断都必须写入规范文档。
- 所有失败必须有面向用户可读的错误提示，并附可复制的 `requestId`（小字展示）；后端按 `requestId` 打印详细日志。
- 代码审查**一次性完整**进行，不做增量式逐条审查。
- 禁止 `if type == "sms"` 之类的因子类型分支，一律用能力断言（前端同样禁止 `if (factor === 'sms')`）。
- 平台不定义授权策略、不做行级 / 密级判定、不提供 `@RequireRole` 这类注解。

### 六、合规要点（必须内建，不是配置出来的）

- 等保二级：单因素即可；等保三级：两种以上组合鉴别技术且至少一种使用密码技术；四级：多因素 + 硬件可信根。
- 等保三级另有：访问控制策略由授权主体配置、粒度到用户级 / 文件与数据库表级、安全标记；审计进程保护、留存 ≥6 个月、三权分立（系统管理员 / 安全管理员 / 审计员）、集中管控、每年渗透测试。
- 密评的三条「身份鉴别」对象不同，不要混谈：
  - 8.2 a) 通信实体（平台 ↔ 业务系统）——mTLS / 国密证书；
  - 8.3 a) 登录设备的运维人员——部署方运维体系承担，不是本平台功能；
  - 8.4 a) 登录用户——本平台本职工作。
- 密评要求传输、存储、认证、签名、校验**全链路国密**；不启用国密 TLS（SM2 证书 / TLCP）则密评不通过，属部署前置项。
- 审计：`auth_events` / `audit_logs` 只增不改不删，触发器禁止 UPDATE / DELETE，HMAC-SM3 链式完整性，按月分区、365 天留存。

### 七、待确认事项（开工前必须裁决并写入规范）

1. **迁移执行方式冲突**：基线《技术栈与工程约定》§6.1 明确「迁移不在应用启动时自动执行」，由发布流程的一次性 Job / init container 执行（避免多副本并发迁移与长锁）；而团队既有规范要求「迁移随后端启动自动执行」。二者矛盾，必须由负责人裁决。
2. **令牌签名算法**：基线已冻结为 `SM3withSM2`（全链路国密，明确不采用 RSA / SHA 系列）；旧 SpIAM 用 RS256（为兼容第三方）。关津按基线走 `SM3withSM2`，但是否保留对外 RS256 兼容路径需确认。
3. **密评目标等级**：索引 §2 写「密评上限二级（因不引入硬件密码模块）」，但合规矩阵与档位清单指出国密 TLS 不启用则密评不通过。需明确目标等级（二级还是三级）及其连带要求。
4. **密码产品路径**：密评要求密码产品达 GB/T 37092 二级及以上；纯软件国密库是否被认可尚未确认。若不认可，需接密码机 / 密码卡，会改变部署形态与成本，应在 M1 前定。
5. **产品代号与仓库名**：规划文档仍写「待定」；新仓库是否命名 `guanjin-next`、放在哪个组织下。
6. **旧仓库定位**：继续维护旧 SpIAM，还是冻结归档、仅作参考。
