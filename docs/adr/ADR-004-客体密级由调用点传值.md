# ADR-004 · 客体密级由调用点传值（不做声明式打标）+ `level` 词表冻结

| 项 | 内容 |
|---|---|
| 状态 | Accepted |
| 日期 | 2026-11-02 |
| 主笔 | 关津 架构 · Ark（TWKJSV）；命名与词表由 Spec（W87AB0）复校、Gate（8WZP9H）落判据 |
| 上位依据 | `decisions.md` **D11**（含补口 **C1/C2/B1**）；索引 §4.2-25（冻结签名五项）、索引 §2「平台不做授权/不做密级判定」；权限模型 §3（SDK 三层判定）、§3.4（未声明即不判定） |

## 1. 背景

基线在「密级」上有三处漂移，任何一处照抄都会造成两套写法：

1. **方法名三套**：`sdk-contract.md` 写 `dataLabel()`；基线示例还出现裸 **`.clearance(3)`**；而索引 §4.2-25 冻结的是 **`role(name).withClearance(level)`**。
2. **`level` 值域未冻结**：示例自相矛盾——`.clearance(3) // 秘密` 与 `dataLabel("order_items", 2) // 秘密`，同一个"秘密"对应两个数。若不冻结，M5 的 `checkLabel`（主体 ≥ 客体）无法唯一判定。
3. **参数名漂移**：`Authz.checkLabel(level)` 与「主体密级 `level`」同名不同义，读代码容易搞反方向。

## 2. 决定

1. **唯一写法 `role(name).withClearance(level)`**；`dataLabel()` 与**裸 `clearance()`** 一并作废，**不得作为别名保留**（"两个方法一个语义"必然分叉）。
2. **客体密级不做声明式打标**：不新增 builder 方法、不新增配置、不新增 SDK API。客体等级由**业务在调用点**把值传给既有能力 **`Authz.checkLabel(objLevel)`**（`GJ-CAP-16` 语义不变）。
3. **形参名冻结**：主体密级 = **`level`**（`withClearance(level)`）；客体密级 = **`objLevel`**（`checkLabel(objLevel)`）。
4. **`level` 词表冻结**：`1 = 内部`、`2 = 秘密`、`3 = 机密`，**数值越大越敏感**；**「公开」= 资源不声明 label → 跳过密级判定，不存在 0 级**（依权限模型 §3.4）。基线 `.clearance(3) // 秘密` 的注释属**笔误**（3 应为机密），与 `dataLabel(...,2) // 秘密` 的矛盾由此消解。
5. **门禁口径**（Gate `AC-ENG-08`③，v9）：禁词两个 `dataLabel(` + 裸 `clearance(`；正则 **`(?<![A-Za-z0-9_])clearance\(`（大小写敏感）**——`withClearance(` 不命中；**扫描范围限 SDK 三语言仓**（源码/`examples/`/`README*`/仓内 `docs/`），**不含 `/docs/` 与基线**（作废声明本身必须能写出旧名）；变异测试**四个注入各验一次**。

## 3. 备选与不选的理由

- **备选 A（保留 `dataLabel()` 作别名，只作废 `.clearance()`）**：否。别名就是第二套写法，"哪个才是权威"会随接入方而不同，等于把口径交给使用方决定。
- **备选 B（引入声明式打标 `dataLabel(resource, level)`）**：否。①索引 §4.2-25 冻结的五项里**没有**客体声明入口，`dataLabel()` 是 SDK 契约自造的第六项；②声明式打标要求平台/SDK 维护一份**客体标签字典**，那是新增数据面，成本远大于收益，而 M5 才用到。
- **备选 C（冻结 `level` 为枚举字符串 `internal/secret/confidential`）**：否。与三方语言的可机械转换规则（枚举值小写 snake）尚可，但基线与 `checkLabel` 语义比较是"数值大小"比较，改字符串要么引入映射表、要么改能力签名 → 属新增契约面。取整数 + 显式词表最省改动。
- **备选 D（保留 0 = 公开）**：否。会多出一个必须判定、但基线明确"未声明就跳过"的悬空级；"公开 = 不声明"让判定函数只需处理 1~3。

## 4. 后果

- **正面**：密级只有一个方法、一个值域、一个参数名；门禁可机械拦住旧写法；M5 的 `checkLabel` 有唯一判定依据。
- **负面 / 需注意**：业务方从旧示例迁移时 `.clearance(3)` 会**直接编译失败**（这是刻意的，比静默改语义安全）；`dataLabel("orders", 1)` 这类**把客体级声明在 builder 上**的老示例要改写为调用点 `checkLabel(objLevel)`。
- **需要谁做什么**：**Nova** 改 `sdk-contract.md` `GJ-CAP-13` 行与全部示例（含 `checkLabel(objLevel)` 改名）、§8 修订点登记；**Ark** 在 S1 的 `scripts/check-forbidden-error-codes.sh` 落两个禁词 + 四个注入的变异用例；**Gate** 已在 `acceptance-criteria.md` v9 落 `AC-ENG-08`③；**Vue/Core 不受影响**（密级判定只在 SDK 本地，平台不做密级判定）。

## 5. 验证方式

- `AC-ENG-08`③：注入 `dataLabel(` → CI 红；注入 `.clearance(` → CI 红；`withClearance(` 不误伤（假阳检查）。
- **本条不进 CH 清单**（不改 key、不改能力数量 22、不改方法签名个数）→ 不影响 `PENDING` 账目；`GJ-CAP-13/16` 的运行时判定用例归 **M5**，M1 不挂判据。
