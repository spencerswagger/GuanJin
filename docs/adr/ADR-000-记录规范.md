## 1. 为什么要 ADR

`/docs/decisions.md` 是**裁定台账**：它回答「两处冲突、以哪一处为准」，按主题编号（`D<n>`）登记，条目多、跨度大，**不适合当工程决策的检索入口**。
ADR 是**单点决策的说明书**：一条 ADR 只回答一个问题——「我们选了什么、为什么不选另一个、将来怎么改」。

两者分工：

| 文件 | 回答什么 | 谁写 |
|---|---|---|
| `decisions.md` | 冲突以谁为准（裁定 + 依据 + 影响面） | **仅 Ark** |
| `adr/ADR-*.md` | 某个决策的上下文、备选、取舍、后果 | Ark（涉及他人模块时先经该模块负责人确认） |
| `/docs/baseline/` | 需求与规格原文 | **任何人不得改（只读）** |

## 2. 编号与命名

- 文件名：`ADR-<三位序号>-<中文短标题>.md`，序号从 `000` 起，**不复用、不重排**；作废的 ADR 保留原文、状态改 `Superseded by ADR-xxx`。
- 一条 ADR 只对应**一个**决策主题；`decisions.md` 的一个 `D<n>` 可以对应 0~1 条 ADR（不是每条 D 都值得写 ADR）。
- ADR **只引用** `D<n>` / `CH<n>` / `AC-<ID>` 编号，**不复制**基线正文；需要复述规格时给「文档名 §章节」指针。

## 3. 固定结构（新 ADR 照抄这七段）

```markdown
# ADR-xxx · 标题

| 项 | 内容 |
|---|---|
| 状态 | Proposed / Accepted / Superseded by ADR-yyy / Rejected |
| 日期 | YYYY-MM-DD |
| 主笔 | 角色 · 名字 |
| 上位依据 | decisions.md 的 D/CH 编号 + 基线「文档 §章节」 |

## 1. 背景（问题是什么，为什么必须做决定）
## 2. 决定（一句话能被执行的口径；含冻结名）
## 3. 备选与不选的理由（至少写一个被否的选项）
## 4. 后果（正面 / 负面 / 需要谁在什么时候做什么）
## 5. 验证方式（哪条 AC / 哪个变异测试 / 哪个命令能证明它生效）
## 6. 变更历史
```

## 5. 硬约束（写 ADR 时不许违反）

1. **不改基线**：`/docs/baseline/` 一个字不改；ADR 只登记「我们怎么实现」。
2. **不改冻结名**：表名（14 张 + `flows`）、端点名（65 个具名）、概念名（档位 / `acr` / `amr` / `purpose` 词表）照抄。
3. **不引缺章**：不引用 `数据模型 §6`、`页面规格 §7`、`接口清单 §6` 这三个不存在的章节（口径见 `D9`）。
4. **不造假通过**：ADR 里的「验证方式」必须是可执行命令或 `AC-<ID>`，不得写「已确认无误」。
